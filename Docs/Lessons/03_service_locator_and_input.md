# Урок 03 — `IInputService`: другий сервіс у контейнері

Мета: урок 02 довів, що механізм "реєстрація → резолв → використання" в `AllServices`
працює для одного сервіса (`IAssetProvider`). Цей урок доводить те саме на зовсім іншому
за природою сервісі — джерелі гравецького вводу, `IInputService`, обгортці над новим
Input System. Це навмисно другий, ще конкретніший приклад "етики роботи із сервісами":
жоден клас гри (і майбутній `PlayerController` уроку 04 теж) не звертається до Input
System напряму — тільки через цей інтерфейс.

Патерни: Service Locator (продовження уроку 02, `Docs/ROADMAP.md` §3 п.2) + Strategy —
розділ 4.10 `ARCHITECTURE_REFERENCE.md` (там Strategy застосований до вибору
Standalone/Mobile реалізації; тут та сама ідея працює на іншій осі — інтерфейс ховає
деталь "як саме зчитується ввід", щоб `PlayerController` міг залежати тільки від
контракту, а не від конкретного способу читання клавіш/стіка).

**Словничок термінів:**

- **Input Actions Asset** — файл-даних Unity (`.inputactions`), у якому описані дії
  гравця (Move, Jump, Fire...) окремо від конкретних клавіш/кнопок, які їх викликають.
- **Action Map** — іменована група дій усередині цього asset'у (наприклад, "Player").
- **Binding** — прив'язка конкретної фізичної клавіші/кнопки/стіка до дії.
- **Composite Binding** — кілька окремих клавіш (W/A/S/D), об'єднаних в один
  двовимірний результат (`Vector2`) однієї дії.
- **Poll** (опитування) — запитати поточне значення "просто зараз", коли самому
  потрібно (`ReadValue<T>()`). **Event/callback** — навпаки, підписатись і отримати
  сповіщення, коли значення змінюється (`.performed`/`.started`/`.canceled`).
- **CallbackContext** — об'єкт, який новий Input System передає в обробник
  event-стилю; з нього дістається саме значення дії.
- **Generate C# Class** — прапорець в інспекторі Input Actions asset'у, який
  автоматично генерує обгортковий клас із готовими полями на кожен Action Map/дію,
  щоб не писати пошук дій по рядкових іменах вручну.

## Що потрібно створити

### 1. Input Actions asset (Unity Editor, не код)

Створи asset типу `Input Actions` (ПКМ у `Project` → `Create → Input Actions`) — місце
вирішуй сам, за аналогією з тим, як для `AssetManagement`/`Services` уроку 02 вже
склалась структура `CodeBase/Infrastructure/<Тема>/`.

Всередині — один Action Map (наприклад, `Player`) і мінімум:
- **`Move`** — тип `Value`, `Vector2`, з Composite Binding `2D Vector` на WASD/стрілки
  (і, за бажання, на лівий стік геймпада).
- Ще **одна-дві кнопкові дії про запас** (наприклад, `Jump`, `Fire`) — тип `Button`.
  Вони нікому не потрібні аж до уроків 04/06, і це нормально: тут це просто дані в
  asset'і, не рядок коду — заводити їх зараз дешевше, ніж повертатись у Input Actions
  Editor двічі. Заборона на "код про запас" (YAGNI, урок 02) стосується логіки/полів у
  C#-класах, а не конфігурації Unity-asset'ів.

Постав галочку **"Generate C# Class"** в інспекторі asset'у — Unity згенерує клас із
готовими посиланнями на Action Map і кожну дію, замість пошуку по рядкових іменах.

### 2. `Infrastructure/Input/IInputService.cs`

Інтерфейс, `IInputService : IService` (той самий маркер, що й `IAssetProvider`).
Потрібно дві речі:

- **Спосіб дізнатись поточний напрямок руху** як `Vector2` — це буде опитуватись
  (poll) кожен кадр із `Update()` майбутнього `PlayerController` (урок 04), тому має
  повертати значення "на запит", а не через підписку.
- **Спосіб дізнатись, що сталась разова дія** (наприклад, натискання `Jump`) — на
  відміну від руху, це дискретна подія, а не безперервне значення. Подумай, чи
  зручніше зробити це методом опитування ("чи натиснуто зараз") чи C#-подією
  (`event Action`), на яку хтось підпишеться — у проєкті вже є приклад
  event-розв'язки (`Action onLoaded` у `SceneLoader` з уроку 01). Обидва підходи
  валідні; обери й будь готовий пояснити чому саме цей.

Форму сигнатур (імена методів/властивостей, чи `event`, чи метод-опитувач) придумуєш
сам — тут є реальне архітектурне рішення, воно не плаский контракт типу `IState`.

### 3. `Infrastructure/Input/InputService.cs`

Реалізація. Всередині створює й тримає екземпляр згенерованого на кроці 1 класу,
**викликає `.Enable()`** на потрібному Action Map (без цього виклику новий Input
System не зчитує нічого — `ReadValue` мовчки поверне нуль, події не спрацюють; це
поширена перша пастка з цим API, тримай у голові).

Метод(и) `IInputService` делегують у виклики до цього внутрішнього об'єкта:
`ReadValue<Vector2>()` для руху, підписку на `.performed` (з відповідним `Enable()`)
для кнопкових дій. Ніхто, крім цього класу, не повинен імпортувати
`UnityEngine.InputSystem` напряму — так само, як лише `AssetProvider` викликає
`Resources.Load` (той самий принцип уроку 02, SRP+DIP).

### 4. Реєстрація сервіса в контейнері

`InputService`, як і `AssetProvider` в уроці 02, має потрапити в `AllServices` через
уже написаний `RegisterService<TService>` — жодних змін у самому `AllServices` не
потрібно (доказ **OCP**: контейнер відкритий для нового типу сервісу, закритий для
модифікації). Де саме в `BootstrapState` це відбувається і в якому порядку відносно
вже зареєстрованого `IAssetProvider` — подивись, як зараз влаштований клас, і виріши
сам.

### 5. Прокидання до `GameLoopState`

`GameLoopState` без `IInputService` не зможе ним скористатись — отже, сервіс має
якимось чином дійти від контейнера до нього. Простеж, як зараз туди доходить
`IAssetProvider` (звідки саме він резолвиться і як передається далі), і застосуй той
самий принцип для `IInputService`. Конкретне місце виклику резолву й форму
конструктора `GameLoopState` обираєш сам.

### 6. Play Mode доказ

У `GameLoopState.Enter()` під'єднайся до `IInputService` так, щоб натискання клавіші
руху чи кнопки-заглушки (`Jump`/`Fire`) виводило `Debug.Log` із фактичним значенням
(наприклад, поточний `Vector2` руху). Це не постійний ігровий функціонал (у
`GameLoopState` поки немає `Update()`-циклу, і не повинно бути — це прийде разом із
`PlayerController` в уроці 04), а разовий смоук-тест: довести, що сервіс реально
резолвиться в робочий екземпляр і реагує на справжній ввід, без пул-опитування щокадру.
Якщо підписався на подію в `Enter()` — не забудь відписатись у `Exit()` (той самий
принцип, що вже застосований в `LoadLevelState.Exit()` для завіси).

## Перевірка

- [ ] Проєкт компілюється без помилок.
- [ ] Input Actions asset створений, `Move` — `Vector2`/composite на WASD, згенерований
      C#-клас підключений.
- [ ] `IInputService : IService`, `InputService` — єдине місце в проєкті, що імпортує
      `UnityEngine.InputSystem`.
- [ ] `InputService` викликає `.Enable()` — без цього нічого не спрацює.
- [ ] Реєстрація в `BootstrapState.RegisterServices()` — той самий патерн, що й для
      `IAssetProvider`, без правок `AllServices`.
- [ ] Play Mode: натискання клавіші руху чи кнопки-заглушки під час `GameLoopState`
      реально виводить лог із значенням у Console.

## SOLID — підсумок по уроку

- **S**RP — `InputService` уміє рівно одне: читати ввід і віддавати його у вигляді,
  зрозумілому решті гри; нічого не знає про рух персонажа чи стрільбу.
- **O**CP — другий сервіс доданий у контейнер без жодної правки `AllServices` чи
  вже написаного `AssetProvider`.
- **I**SP — `IInputService` тримає лише те, що реально споживається (рух + разові
  дії), а не весь API згенерованого Input System класу.
- **D**IP — усе, що прийде пізніше (`PlayerController`, `WeaponShooter`), залежатиме
  від `IInputService`, не від конкретного `InputService` чи від `UnityEngine.InputSystem`
  напряму — реалізацію можна буде підмінити (наприклад, реплей-запис вводу для тестів)
  без зміни жодного споживача.

## Опційне ДЗ із зірочкою (не блокує перехід до уроку 04)

З конспекту оригінального курсу (`Docs/ROADMAP.md` §4) — урок про DI-контейнер там мав
два опційні розширення:

1. **Lifecycle/dispose для сервісів.** Зараз сервіси живуть, поки жива гра — це
   свідоме спрощення (як і в референс-проєкті). Подумай (можна просто словесно,
   не обов'язково кодом): що мало б статись із `InputService`, якби гру можна було
   призупинити на паузі так, щоб ввід гравця ігнорувався? Чи потрібен окремий
   `Enable()`/`Disable()` виклик ззовні, чи цього достатньо всередині самого
   `PlayerController`?
2. **Constructor-only авто-резолвер.** Зараз кожна залежність прокидується вручну,
   рядок за рядком (`GameStateMachine` явно дістає `IAssetProvider`, `IInputService` і
   передає їх у конструктори). Спробуй (окремим експериментальним класом, не чіпаючи
   робочий код) написати маленький резолвер, який через рефлексію дивиться на типи
   параметрів конструктора й сам підставляє відповідні сервіси з `AllServices` —
   без атрибутів на класі. Це не потрібно для гри, це вправа на розуміння, що саме
   DI-контейнери роблять "під капотом".

показав код — переходимо до рев'ю, а після нього — до уроку 04 (`PlayerController`,
перший реальний споживач `IInputService`).
