# Делегати, `event` і підписки

Уперше трапилось: урок 01, `SceneLoader.Load(...)` / `LoadLevelState.onLoaded` (делегат
як одноразовий колбек). Урок 03 додав другий випадок — довготривала підписка
(`event`) для `IInputService`, і третій — подія, яка передає параметр
(`InputAction.CallbackContext`). Це один об'єднаний конспект, бо всі три — варіації
однієї механіки (делегат), не три різні теми.

## 1. Що таке делегат

Делегат — тип, значенням якого є **посилання на метод**, а не на дані. Усі "звичайні"
типи (`int`, `string`, твій власний клас) описують дані; делегат описує "щось, що можна
викликати" — конкретний метод з певною сигнатурою (параметри + тип результату).

## 2. Скільки різних вбудованих делегатів є — `Action`/`Func`-родина

.NET визначає дві родини готових generic-делегатів, розрізнені лише кількістю
параметрів і тим, чи є результат:

| Тип | Параметрів | Повертає |
|---|---|---|
| `Action` | 0 | нічого (`void`) |
| `Action<T>` | 1 | нічого |
| `Action<T1, T2>` | 2 | нічого |
| ... | до 16 типів-параметрів | нічого |
| `Func<TResult>` | 0 | `TResult` |
| `Func<T, TResult>` | 1 | `TResult` |
| ... | до 16 типів-параметрів | `TResult` |

Тобто "скільки їх" — не фіксоване мале число: `Action`/`Func` є з 0 до 16
параметрів, обираєш за тим, скільки аргументів приймає метод, який хочеш передати.
На практиці рідко потрібно більше 1-2. У проєкті поки трапились тільки `Action` (0
параметрів) і `Action<InputAction.CallbackContext>` (1 параметр).

Є ще третій варіант — **власний named delegate** через ключове слово `delegate`:

--------------------------- КОД ---------------------------
<pre>
public delegate void ScoredHandler(int points);
</pre>
------------------------------------------------------------

Робить те саме, що `Action<int>`, але з власною, читабельнішою назвою типу замість
generic-запису. У проєкті поки не знадобився — `Action`/`Action<T>` покривають усе, що
є, і `event Action<int> Scored` виглядає не гірше за `event ScoredHandler Scored`.

## 3. Одноразовий колбек: `Action` як звичайний параметр

**Приклад із проєкту** — `LoadLevelState.cs` / `SceneLoader.cs` (урок 01):

--------------------------- КОД ---------------------------
<pre>
// LoadLevelState.cs
public void Enter(string sceneName)
{
    _loadingCurtain.Show();
    _sceneLoader.Load(sceneName, onLoaded);
}

private void onLoaded() =&gt; _stateMachine.Enter&lt;GameLoopState&gt;();
</pre>
------------------------------------------------------------

--------------------------- КОД ---------------------------
<pre>
// SceneLoader.cs
public void Load(string sceneName, Action onLoaded = null)
{
    if (SceneManager.GetActiveScene().name == sceneName)
        onLoaded?.Invoke();
    else
        _coroutineRunner.StartCoroutine(LoadScene(sceneName, onLoaded));
}
</pre>
------------------------------------------------------------

`_sceneLoader.Load(sceneName, onLoaded)` передає `onLoaded` **без дужок** — не
викликає, а передає посилання на метод. Компілятор сам загортає пару "цей метод + цей
екземпляр `LoadLevelState`" у делегат-об'єкт (**method group conversion**), бо
цільовий параметр очікує `Action`. `Action onLoaded` усередині `SceneLoader` — це
звичайний параметр методу, той самий механізм, що й `string sceneName` поруч, тільки
тип інший; окрема змінна не потрібна, сам параметр і є "місцем зберігання" на час
виконання методу.

`onLoaded?.Invoke()` виконує метод, загорнутий у делегат; `?.` захищає від
`NullReferenceException`, якщо викликати `Load` без колбека (звідси й `= null` за
замовчуванням у сигнатурі).

**Чому саме так, а не прямий виклик:** якби `SceneLoader` сам викликав щось на
кшталт `_stateMachine.Enter<GameLoopState>()` напряму, він був би змушений знати про
`GameStateMachine` — зайва залежність і порушення SRP. Через `Action`-колбек
`SceneLoader` каже "я завантажу сцену і повідомлю, викликавши те, що мені дали", і
йому байдуже, що саме викликається.

Це — **одноразовий** колбек: викликається рівно один раз, після чого делегат нікому
більше не потрібен. Наступний розділ — інший випадок: коли треба підписатись
надовго і отримувати сповіщення про **кожне** повторення події.

## 4. Довготривала підписка: `event`

`event Action Ringing` — спрощено, **список посилань на методи** (multicast
delegate), який зберігає клас-власник. `+=` не викликає нічого — він **додає** метод
у цей список. `-=` — **видаляє** з нього. Коли власник робить `Ringing?.Invoke()`, він
проходить по всьому поточному списку й викликає кожен метод, що там є:

--------------------------- КОД ---------------------------
<pre>
_alarmClock.Ringing += OnAlarm;    // список: [OnAlarm]
_alarmClock.Ringing += OnSnooze;   // список: [OnAlarm, OnSnooze]
_alarmClock.TriggerAlarm();        // викличе ОБИДВА
_alarmClock.Ringing -= OnAlarm;    // список: [OnSnooze]
</pre>
------------------------------------------------------------

Ніякої магії — це такий самий список, як `List<Action>`, тільки з вбудованою мовною
підтримкою `+=`/`-=`/`Invoke()` замість `.Add()`/`.Remove()`/`foreach`.

**Звідки береться сам метод `Invoke()`:** це не щось, що треба писати самому —
**кожен** делегат (`Action`, `Action<T>`, `Func<T>`, будь-який) автоматично має
вбудовані методи `Invoke()`/`BeginInvoke()`/`EndInvoke()`, згенеровані компілятором
разом із самим типом делегата. `Ringing?.Invoke()` — це не оголошення нового методу,
а виклик **уже готового** методу на об'єкті `Ringing` (з `?.` перед ним, щоб не
впасти на `NullReferenceException`, якщо підписників ще нема). Метод, який реально
**написаний** тут — це `TriggerAlarm()` (чи інша функція, всередині якої стоїть цей
рядок).

**Наскрізний приклад (ізольований):**

--------------------------- КОД ---------------------------
<pre>
public interface IAlarmClock
{
    event Action Ringing;
}

public class AlarmClock : IAlarmClock
{
    public event Action Ringing;

    public void TriggerAlarm() =&gt; Ringing?.Invoke();
}

// десь у споживачі:
_alarmClock.Ringing += OnAlarm;   // підписка
_alarmClock.Ringing -= OnAlarm;   // відписка

void OnAlarm() { /* ... */ }
</pre>
------------------------------------------------------------

### Чому подія оголошується в класі, що її викликає, а не в тому, хто підписується

Знання "коли саме настав момент X" фізично є тільки в `AlarmClock` — він один
слідкує за часом. Право сказати "зараз!" (викликати `Invoke()`) має належати тому,
хто це знає. Якби подія жила деінде (наприклад, у `Player`), `AlarmClock` був би
змушений тримати посилання на конкретний клас `Player`, щоб якось йому про це
сповістити напряму — а це вже пряма залежність.

**Аналогія:** газета (видавництво) веде список підписників і сама вирішує, коли
надрукувати номер і розіслати. Підписник не може змусити газету щось надрукувати —
він тільки каже "додай мене в список" / "прибери мене". Право *ініціювати* розсилку
лишається за видавцем.

### Навіщо саме `event`, а не звичайне публічне поле

Без слова `event` — `public Action Ringing;` — це теж скомпілюється і `+=`/`-=` теж
працюватимуть. Але звичайне поле **не захищене**: чужий клас може випадково:

--------------------------- КОД ---------------------------
<pre>
_alarmClock.Ringing = SomeHandler;   // ПЕРЕЗАПИСУЄ весь список — усі попередні
                                       // підписники мовчки зникають
_alarmClock.Ringing.Invoke();         // чужий клас сам "вдає" AlarmClock і
                                       // ініціює подію, хоча нічого не сталось
</pre>
------------------------------------------------------------

`event` забороняє обидві дії **на рівні компілятора** — ззовні класу-власника
дозволені лише `+=`/`-=`. Це та сама ідея інкапсуляції, що й `private`-поле з
публічним get-only-доступом — тільки для делегатів.

### Чому це послаблює залежність (не лише про захист від помилок)

**Без event (жорстка залежність):**
--------------------------- КОД ---------------------------
<pre>
public class AlarmClock
{
    private Player _player;               // AlarmClock ЗМУШЕНИЙ знати клас Player

    public void TriggerAlarm() =&gt; _player.WakeUp();
}
</pre>
------------------------------------------------------------
Якщо завтра з'явиться ще й `Robot`, якому теж треба реагувати — доведеться лізти
всередину `AlarmClock` і дописувати виклик. Порушення OCP.

**З event (слабка залежність):**
--------------------------- КОД ---------------------------
<pre>
public class AlarmClock
{
    public event Action Ringing;          // знає лише про System.Action
    public void TriggerAlarm() =&gt; Ringing?.Invoke();
}
</pre>
------------------------------------------------------------
`Player`, `Robot`, чи хто завгодно ще підписується сам, без жодної правки
`AlarmClock`. `AlarmClock` навіть не знає, чи є взагалі хтось підписаний — звідси
`?.` перед `Invoke`: якщо список порожній (`null`), виклику просто не станеться.

## 5. Подія з параметром: `event Action<T>`

Усе вище — події **без** параметра: підписник дізнається лише "щось сталось", без
деталей. Але подія може передавати дані підписнику — так само, як звичайний метод
приймає параметри.

**Ізольований приклад:**

--------------------------- КОД ---------------------------
<pre>
public class Referee
{
    // подія з параметром: підписник отримає int (скільки очок забито)
    public event Action&lt;int&gt; Scored;

    public void Score(int points) =&gt; Scored?.Invoke(points);
}

public class Scoreboard
{
    private readonly Referee _referee;

    public Scoreboard(Referee referee)
    {
        _referee = referee;
        _referee.Scored += OnScored;   // підписка — у конструкторі
    }

    // сигнатура ОБОВ'ЯЗКОВО має відповідати Action&lt;int&gt;:
    // один параметр int, повертає void
    private void OnScored(int points) =&gt; Console.WriteLine($"+{points} очок!");
}
</pre>
------------------------------------------------------------

Ключове: коли підписуєшся методом (`+= OnScored`, без дужок), компілятор перевіряє,
що **сигнатура методу** (типи параметрів, тип результату) збігається з типом
делегата події. `OnScored()` без параметра тут не скомпілюється.

**Проєкція на новий Input System (урок 03):** `_inputActions.Player.Jump.performed`
має тип `Action<InputAction.CallbackContext>` — той самий принцип, що `Action<int>`
вище, тільки замість `int` — об'єкт `InputAction.CallbackContext` (з нього можна
дістати `context.ReadValue<T>()`, якщо деталі натискання потрібні; для простого
"кнопку натиснуто" параметр можна ігнорувати в тілі обробника).

## 6. Одне джерело — кілька різних подій одночасно

До цього уроку кожен клас у проєкті мав щонайбільше одну релевантну подію
(`onLoaded`). Новий Input System показує інший випадок: **одна дія має відразу три
окремі, незалежні події**, кожна для свого моменту:

- `action.started` — момент початку взаємодії (кнопку почали тиснути).
- `action.performed` — дія фактично відбулась (для кнопки — зазвичай той самий момент,
  що й `started`; для аналогових/утримуваних дій може відрізнятись).
- `action.canceled` — взаємодію перервано (кнопку відпустили).

Підписуєшся окремо на ту (ті), що потрібні — необов'язково на всі три. Це не новий
механізм, а три окремі екземпляри `event Action<InputAction.CallbackContext>` на
одному об'єкті `action`.

**Не забувати відписатись**, якщо підписався — той самий принцип, що вже
застосований для завіси в `LoadLevelState.Exit()`: підписка без відписки — витік
пам'яті/пізніше подвійний виклик обробника, якщо об'єкт перестворюється. Детальніше,
з конкретними прикладами коли саме потрібно, а коли ні (і чому лямбда заважає
відписатись) — [`InputAction_Events_and_CallbackContext.md`](InputAction_Events_and_CallbackContext.md) §8.

## 7. Інші форми подій, які трапляться поза цим проєктом (для впізнавання, не для використання тут)

- **`EventHandler`/`EventHandler<TEventArgs>`** — старий (.NET, ще з часів WinForms)
  конвенційний формат події: `void Handler(object sender, TEventArgs e)` — перший
  параметр завжди "хто викликав", другий — дані у спеціальному класі-нащадку
  `EventArgs`. Побачиш його в багатьох чужих/старіших C#-кодбейзах. У цьому проєкті
  не використовується — `Action`/`Action<T>` простіше, і `sender` тут нікому не
  потрібен.
- **`UnityEvent`/`UnityEvent<T>`** (`UnityEngine.Events`) — Unity-специфічний аналог
  `event`, який можна налаштувати **в Inspector'і** (наприклад, `Button.onClick` у
  UI). Це окремий клас (не мовна конструкція `event`), серіалізується Unity. Підписка
  через `.AddListener(method)`/`.RemoveListener(method)` замість `+=`/`-=`, та сама
  ідея "список методів":

  --------------------------- КОД ---------------------------
  <pre>
  using UnityEngine;
  using UnityEngine.UI;

  public class PauseMenuTest : MonoBehaviour
  {
      [SerializeField] private Button _resumeButton;

      private void Awake() =&gt; _resumeButton.onClick.AddListener(OnResumeClicked);

      private void OnResumeClicked() =&gt; Debug.Log("Resume clicked!");

      private void OnDestroy() =&gt; _resumeButton.onClick.RemoveListener(OnResumeClicked);
  }
  </pre>
  ------------------------------------------------------------

  Той самий принцип "рушій сам нічого не зберігає, лише виявляє й диспетчерить", що
  й у Input System (§6 вище, і детальніше в
  [`InputAction_Events_and_CallbackContext.md`](InputAction_Events_and_CallbackContext.md)):
  Unity `EventSystem` щокадру сама перевіряє клік мишкою/дотик, знаходить **конкретну**
  кнопку під курсором і викликає **її власний** `onClick.Invoke()` — сам `EventSystem`
  списку підписників не тримає, це власність кожної окремої кнопки. У цьому проєкті
  сервіси — звичайні C#-класи без Inspector, тому `UnityEvent` поки не застосовується;
  знадобиться, коли з'явиться перший UI-екран (наприклад, меню паузи).
