# Shadowing: локальна змінна ховає поле

Уперше трапилось: урок 02, `BootstrapState.RegisterServices()` — реальний баг студента,
не вигаданий приклад.

## Що сталося в коді

--------------------------- КОД ---------------------------
<pre>
public class BootstrapState : IState
{
    private AllServices _services;          // поле класу

    public BootstrapState(GameStateMachine gameStateMachine, SceneLoader sceneLoader, AllServices services)
    {
        _services = services;               // тут усе правильно: поле = переданий контейнер
        RegisterServices();
    }

    private void RegisterServices()
    {
        AllServices _services = new AllServices();   // ← ось бага
    }
}
</pre>
------------------------------------------------------------

Усередині `RegisterServices()` оголошена **нова локальна змінна**, яка випадково має
**те саме ім'я**, що й поле класу — `_services`. З точки зору компілятора це абсолютно
легальний код, помилки компіляції не буде.

## Чому це працює саме так (правило області видимості)

Коли в тілі методу є локальна змінна з тим самим ім'ям, що й поле класу — усередині
цього методу будь-яке звернення до цього імені означає **локальну змінну**, а не поле.
Локальна декларація "затуляє" (shadow) поле на весь час своєї області видимості. Це не
помилка компілятора — це стандартне правило видимості C#: пошук імені йде від
найближчої області (метод) назовні (клас), і як тільки ім'я знайдено локально, пошук
зупиняється.

Наслідок у цьому конкретному коді:
- Поле `_services` (яке за межами цього методу справді містить переданий
  `AllServices.Instance`, дивись `GameStateMachine.cs`: `new BootstrapState(this, sceneLoader, AllServices.Instance)`)
  усередині `RegisterServices()` просто недосяжне — компілятор бачить лише локальну
  змінну.
- `new AllServices()` створює **другий, окремий, порожній** контейнер сервісів — жодного
  стосунку до того єдиного `AllServices.Instance`, яким користуватиметься решта гри
  (наприклад, майбутній `GameLoopState`, коли питатиме `GetService<IAssetProvider>()`).
- Локальна змінна нікуди далі не передається і не використовується — рядок фактично
  мертвий код: щось створюється і одразу губиться.

## Як цього уникати

- Не називай локальну змінну так само, як поле класу, особливо коли в методі це поле
  взагалі не мало використовуватись напряму (тут кожен виклик "зареєструвати сервіс" мав
  іти через уже наявне поле `_services`, без створення нового об'єкта).
- Якщо справді треба звернутися саме до поля, а не до локальної змінної з тим самим
  ім'ям, є явний спосіб — `this.Ім'яПоля` (кваліфікатор `this` завжди означає "поле/член
  класу", ігноруючи локальні тіні). Але найнадійніший захист — не створювати колізію імен
  узагалі.
- Більшість лінтерів/IDE (Rider, Visual Studio) підсвічують shadowing попередженням —
  варто звертати увагу на жовті підкреслення для локальних змінних з "надто знайомими"
  іменами.

## Підсумок: бібліотечні типи тут

Немає — shadowing — правило видимості імен самого компілятора C#, не пов'язане з
жодним типом із бібліотеки. Усі типи в прикладі (`BootstrapState`, `AllServices`,
`GameStateMachine`) — проєктні класи.
